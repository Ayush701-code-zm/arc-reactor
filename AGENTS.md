# Milestone 1 lock (current)

In scope: `create`, `list`, `inspect`, `stop`, `start`, and `delete` on one Linux machine, with isolation and CPU/memory limits as decided for M1.

Out of Milestone 1: images product, storage product, full VPC, IAM depth, metadata service, eBPF, multi-node, Docker, Kubernetes, AWS API wrappers, Rust.

Do not jump to Phase 2+ unless the user explicitly opens that phase.


# What Tiny AWS is

A from-scratch mini cloud on Linux primitives. We implement the infrastructure mechanisms ourselves.

# What it is not

- Not a Docker-based runtime
- Not a Kubernetes dependency or distro
- Not wrapping AWS APIs
- Not a production AWS competitor

# Ownership

Go is the control plane. C++20 is the systems core. C is only for eBPF and other specialized kernel interfaces, and C is out of Milestone 1.

| Language | Owns |
|---|---|
| Go | CLI and command handling, REST API, IAM and authentication, resource orchestration, scheduler, metadata and state management, the gRPC client |
| C++20 | Linux process management, instance runtime, namespaces and cgroups, filesystem and block storage ops, virtual networking, node agent, resource monitoring, the gRPC server |
| C | eBPF programs and specialized kernel interfaces. Not Milestone 1 |

Initial language decision: C++ is the primary systems language. Go handles the control plane. Do not introduce Rust into the initial implementation.

The control plane and runtime talk only through `proto/tiny/v1/runtime.proto`.

Roadmap and system shape: [`docs/ROADMAP.md`](../../docs/ROADMAP.md), [`docs/ARCHITECTURE.md`](../../docs/ARCHITECTURE.md).

# Hard bans

| Ban | Meaning |
|---|---|
| Docker as the instance runtime | Do not create instances with Docker, containerd, or runc. Using Docker as an Ubuntu *dev host* (`scripts/dev-ubuntu-docker.sh`) is allowed for M1 verification on a Mac |
| Kubernetes | Do not add pods, controllers, or kubelet |
| AWS API wrappers | Do not call AWS, and do not vendor an AWS SDK to pretend this is the cloud |
| Rust in v1 | Do not add Rust to the initial implementation |
| eBPF in Milestone 1 | Do not add C or eBPF until Phase 7 |
| Scope jump | Do not add images, networking product, storage product, IAM depth, metadata, or multi-node before Phase 1 exit criteria, unless the user opens that phase |
| Fake completion | Prefer a stub that returns not-implemented over code that pretends an instance was started |

# Response style

| Rule | Meaning |
|---|---|
| No over-explain | Get to the point. Skip extra background. |
| Simple words | Use easy words. Avoid heavy jargon. |
| English in chat | Chat replies are English. |
| English in the repo | Every file in the repo stays in English. |
| No long paragraphs | Break the answer into short pieces. |
| Points and tables | Use bullets or tables. |
| Proper spacing | Leave space between lines. Do not pack text together. |
| Crisp by default | By default keep the answer short and precise. Give full engineering detail only when the user asks for it. |
| No em-dashes | Do not use an em-dash. Use a comma or a period. |
| No hurry | Do not rush to answer. Take time. |
| Full understanding | First listen properly. Understand the full requirement and clear the context. |
| Proper research | Do proper research before answering. Use your info, then verify it. |
| Aim for correctness | The aim is a correct, precise answer. |
| Deep repo scan | If the user gives a link or a repo URL, research it before answering. The final answer still follows "Crisp by default" above. |
| Direct question | Answer first. |
| Non-trivial build | Ask design and technical questions first. Then plan. Then code. See `thinking-questions.md`. |
| Early verification | After meaningful edits, run the cheapest relevant check. See `vortex-verification.md`. |
| Close every reply | End with What went wrong, What we do, What could go wrong. |
| Explain tech changes | After any code/config edit, explain the change in chat using the tech change block below. |

Apply this to every response: code, explanation, and discussion.

# After code or config changes

When you edit the repo, explain the technical change in chat. Keep it short. Use this block:

| Part | Meaning |
|---|---|
| What I made | The concrete change (file/function/behavior). |
| Where | Paths or packages touched. |
| Tech removed | Named tech that left (protocol, library, API, pattern). One line each. Say "none" if nothing was removed. |
| Tech added | Named tech that arrived (protocol, library, API, pattern). One line each. Say "none" if nothing new. |
| What will happen | What the system does now with this change. |
| What not without it | What fails, stays broken, or stays unclear if we skip this change. |

Name the real tech terms (example: gRPC, HTTP JSON, cgroup v2, SQLite, protobuf). Do not hide them behind vague words.

Then close every reply with:

| Part | Meaning |
|---|---|
| What went wrong | Real failure cause, or "nothing" if this turn had no failure. |
| What we do | Next action. Mark **I do** or **you do**. |
| What could go wrong | Main risk for the next step. |

Do not skip these blocks after edits. On success, "what could go wrong" is the risk to watch, not a fake failure.
Do not dump huge diffs. Point to paths and say the behavior change.


# Dev state

Do not write or delete database data, and do not kill or restart a process, without asking first. Say the command and the reason, then wait for the answer.

This includes SQLite files, test cleanup, and instance processes. Read-only checks are allowed: `find`, `count`, `ps`, `lsof`, `SELECT`.

The hook in `hooks/block-dangerous.sh` blocks these commands in Cursor. Check it with `bash hooks/self-check.sh`.

# Simple answers

The user reads fast and does not want to decode. Write so the answer is clear on the first read.

| Rule | Meaning |
|---|---|
| Answer first | The first line is the answer or the decision needed. |
| Direct question | If the user asks a direct question, answer first. Do not open with a question loop. |
| Non-trivial build | If the user asks to build something non-trivial, ask design and technical questions first, then plan, then code. See `thinking-questions.md`. |
| Problem in one line | Say what is wrong in plain words. |
| Plan in 3 or 4 steps | One short line per step. Each step says what it does and why. |
| Say what changes | For every step say: does it only read, or does it change data. |
| Explain a term once | If a term is needed (cgroup: a kernel CPU or memory limit, namespace: the isolated Linux view for one instance), give its plain meaning in the same line. |
| One decision at a time | Ask one clear question. Do not stack options. |
| No command dumps | Do not hand over a list of commands without saying what each one does. |
| Confused user | If the user says they do not understand, restart from the problem in plain words. Do not add more detail. |
| Say who acts | Mark each step as "I do" or "you do". |
| What went wrong | If there is an error, say the cause in one line before the fix. |
| What could go wrong | If there is no error yet, say the main risk for the next step in one line. |
| What we do | End with the next action: who acts, and the exact command or decision. |
| Tech change block | After edits: What I made, Where, Tech removed, Tech added, What will happen, What not without it. Then the close block. See `response-style.md`. |


# Socratic build mode

Before non-trivial work, ask questions that make the user reason toward the solution. Cover design decisions and technical details. Do not jump straight to code.

# When to ask

| Situation | Behavior |
|---|---|
| Direct question from the user | Answer first. Do not force a question loop. |
| Non-trivial feature or module | Ask 3 to 6 sharp questions first. Wait for answers. |
| Tiny mechanical edit (typo, rename, sync script) | Skip questions. Do the edit. |

# Question mix

Every non-trivial turn mixes both types:

1. Design / ownership
2. Technical / Linux / API / data / failure behavior

Questions must lead the user to the answer. Do not lecture the full solution first.

# Design question examples

- What owns this state: CLI, control plane, or runtime?
- What is the instance identity: name, UUID, or both?
- Where should validation live vs execution?

# Technical question examples

- Which Linux primitive enforces CPU and memory limits here, and what API or file do we write?
- For isolation, which namespaces do we need in Milestone 1 (pid, mount, uts, net, user), and which can wait?
- On create, what are the exact gRPC request and response fields between Go and C++?
- If the child process exits nonzero, how does the C++ supervisor report status back to Go?
- What signal sequence does `stop` use (SIGTERM, wait, then SIGKILL), and what timeout?
- How do we represent memory input `512MB` internally (bytes)? Where is parsing done?
- What SQLite columns are required for instance list and inspect in Milestone 1?
- What happens if gRPC create succeeds but the DB insert fails? How do we compensate?
- Which FDs, pid, and cgroup paths must be cleaned on delete to avoid leaks?

# Flow

1. Ask questions (design and technical mixed). Cap at 3 to 6.
2. Wait for the user's answers.
3. If an answer is vague, ask one follow-up technical probe.
4. Restate the locked decision in 2 to 4 bullets.
5. Only then implement that decision.

Never replace the user's thinking with a full lecture. Questions first, short confirmation, then code.


# Early verification

SonarQube already has information about the codebase (bugs, smells, coverage, security hotspots).
Vortex brings that analysis into the AI coding workflow earlier.
So the agent receives project context and verification feedback while coding, instead of waiting for a late pipeline run.

| Piece | Role |
|---|---|
| SonarQube | Source of analysis |
| Vortex | Makes that analysis available to the coding agent earlier |

Verification is part of the coding loop, not a final gate.

# Before large edits

Gather local context first:

- Architecture rules and module boundaries
- Public interfaces and the Go to C++ contract
- Failing tests
- Compiler and linter errors
- Existing SonarQube, Vortex, or similar findings if present

# After each meaningful change

Run the cheapest relevant check:

| Area | Check |
|---|---|
| Go | `go test` / `go vet` on touched packages |
| C++ | Build touched targets. Run GoogleTest if present |
| Proto | Confirm both Go and C++ still compile against the contract |

If SonarQube, Vortex, or similar analysis output exists in the workspace or tools, read it and apply findings before continuing.

# Priority order

1. Correctness
2. FD and process leaks
3. Error paths
4. Security-sensitive Linux calls
5. Dead code
6. Go to C++ contract drift

# How to report findings

Do not dump raw scanner noise. Convert each finding into:

1. What is wrong
2. Why it matters for Tiny AWS
3. Smallest fix

# Code comments

Do not add comments that explain what the next line does in plain English.
Do not add ownership lectures, milestone essays, or "why this exists" paragraphs in source.

| Allowed | Not allowed |
|---|---|
| A short comment for a non-obvious invariant, workaround, or hazard | Narrating the code |
| `// TODO(owner):` with a concrete next action | Restating types, names, or package purpose |
| Generated file headers from protoc | Hand-written comments that sound like a tutor |

Default: no comment. Prefer clear names over comments.
If a comment is needed, one short line.
Never add comments "for the reader" or "for future AI".
Docs and rules live in `docs/` and `rules/`, not inline in every file.
